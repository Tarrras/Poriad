# Рев’ю імпорту подій — 2026-09-11

Це початкове рев’ю до реалізації. Виконані того ж дня виправлення й результати перевірок
описані в [журналі оновлення](ingest-improvements-2026-09-11.md).

Перевірено `tools/ingest` і `tools/probe_event_sources.py`: читання коду, штатні офлайн-тести, додаткові синтетичні відтворення та актуальні вебсторінки джерел. Повний мережевий обхід усіх міст і застосування SQL до PostgreSQL не виконувалися. Відомості про кількість подій у старому README не перевиміряні. Код конвеєра та наявні незакомічені зміни не змінено.

## Висновок

Основа конвеєра придатна для розвитку: окремі fetch/extract/normalize/venue/emit, повторювані UUID, SQL upsert, геокодування й офлайн-тести. Головні прогалини — життєвий цикл подій, повнота обходу та ідентичність сеансів. Збільшення кількості джерел без цих виправлень збільшить і кількість помилкових публікацій та втрат.

## Відтворені результати

`python3 -m tools.ingest.test_ingest` — усі наявні перевірки пройшли. Додаткові прямі виклики поточних функцій дали:

```text
cancelled accepted: True
city and coordinates: ('Львів', 50.45, 30.53)  # використано київський індекс
two sessions extracted: 1                    # очікується 2
long title length: 121                       # ліміт 120
non-transitive dedupe:
  a duplicate of b
  b published
  c duplicate of a                          # a вже відкинуто
b equals c: False
non-finite price: (nan, False)
```

Трійка для дедуплікації: a=«Альфа Бета», b=«Альфа Гамма», c=«Бета Дельта», однакові час/координати, ваги 0.7/0.8/0.6. Це синтетичні контрприклади; кількість аналогічних випадків у живих дампах не виміряна.

## Прогалини інструмента дослідження

`probe_event_sources.py` використовує окремий спрощений JSON-LD-парсер без @graph/ItemList; це дає хибні нулі. Він не використовує HTTP-політику конвеєра, не перевіряє HTTP-код curl, визначає свіжість sitemap за lastmod і захардкодженим 2026. lastmod — дата зміни сторінки, а не дата проведення. Internet-Bilet узагалі відсутній у LISTINGS.

Переробити probe на той самий fetch/extract/normalize, що й імпорт. Зберігати для кожного джерела дату перевірки, HTTP-статус, кількість витягнутих/майбутніх/скасованих/з гео/унікальних подій, часовий горизонт, причини відмов і версію адаптера. HTML-знімки або мінімальні fixtures дозволять повторювати перевірки без мережі.

## Рекомендований порядок реалізації

1. Регресійні тести й виправлення P1: статуси, місто/гео, ліміт заголовка, дедуплікація; вимкнення автоматичного retire для недоведено повних вибірок.
2. Структурований результат обходу: complete/partial/failed, seen окремо від publishable, причини відмов, retry, manifest SQL. Перевірка згенерованого SQL в одноразовій локальній базі зі схемою проєкту.
3. Сумісна ідентичність сеансів та збереження provenance. Переноси не повинні створювати зайві записи чи ламати збережені події.
4. Пагінація та обмежене дозавантаження детальних карток; джерело скасувань Karabas.
5. TicketsBox, DOU та доопрацювання Моє місто; далі прямі майданчики. Для кожного — fixtures, звірка часу з видимою сторінкою, кількості унікальних живих подій і частки невизначених адрес.

Критерій «жива»: підтверджені актуальні дата/місце, немає відомого скасування чи переносу без нової дати, збережені час останньої перевірки та походження статусу. HTTP 200, майбутня дата або кнопка «Купити» окремо цього не гарантують.
