## Джерела з обмеженнями

- [TicketsBox Харків](https://kharkiv.ticketsbox.com/) та [Дніпро](https://dnipro.ticketsbox.com/):
  повторна проба дала HTTP 200, але нуль Event JSON-LD і нуль HTML-посилань із `/event/`.
  Це результат перевіреного способу обходу, а не доказ відсутності подій у місті.
- [Kharkiv IT Cluster](https://it-kharkiv.com/events): переглянута перша сторінка показує
  8–10 вересня, онлайн та навіть Стамбул. Потрібні пагінація й перевірка фактичного міста;
  контактна адреса кластера не є адресою кожного заходу. Майбутніх офлайн-подій саме Харкова
  в цій вибірці не підтверджено.
- [LoveOdessa](https://love-odessa.od.ua/uk/tour-schedule/): видимий розклад містить щоденні
  екскурсії та пропозиції, які тимчасово не проводяться. Штатний fetch відмовив через перевірку
  robots. Код однаково повідомляє заборону при недоступному robots і при явному disallow,
  тому точну причину ще треба розрізнити. До автоматичного імпорту джерело не готове.
- Сторінка з майбутньою датою, реєстрація на курс, період роботи виставки та доступна для
  бронювання екскурсія — різні сутності. Не можна множити щоденні «івенти» з годин роботи
  закладу чи обіцянки «щодня» без перевіреного розкладу сеансів.

## P0: точніше підтверджувати актуальність

1. **Окремий адаптер [скасувань і переносів Karabas](https://karabas.com/info/).**
   Є таблиця URL, міста, статусу, попередньої та нової дати, а також пагінація.
   Перевірений приклад: львівські «Світові хіти у виконанні оркестру» перенесено з
   11.09.2026 18:30 на 20.09.2026 18:30. Це дозволяє адресно оновити старий сеанс,
   навіть якщо JSON-LD не дає previousStartDate. HTML дублює записи для різних екранів;
   іноді поля цих копій різняться. Конфлікти відправляти на review. Час таблиці перевіряти
   окремо: не застосовувати механічно поправку `utc_is_local` від JSON-LD Karabas.
2. **Облік перевірок на рівні джерела і сеансу.** Запропоновані поля: `last_checked_at`,
   `last_seen_at`, `last_successful_fetch_at`, `status_evidence_url`, повнота обходу.
   Мережева помилка не оновлює last_seen і не означає скасування. Частковий обхід не
   дозволяє знімати відсутні записи. Явне скасування — сильніше за застарілу позитивну копію.
3. **Повторна перевірка перед початком.** Початкова пропозиція політики: до 48 годин —
   перевірка раз на 6 годин; до 7 днів — щодня; далі — раз на 3 дні. Це налаштування,
   які потрібно скоригувати за навантаженням/robots. Довга непідтвердженість означає
   `stale/review`, а не автоматично `cancelled`.
4. **Сталий event ID та походження полів.** Зберігати зв’язки всіх source sessions із
   канонічною подією; обирати час, адресу і статус за перевіреними правилами та їхньою
   свіжістю. Зникнення одного продавця не повинне створювати новий event ID. Перенос
   повинен залишати історію попередніх дат. Це потребує окремої зміни моделі з міграцією.

## P1: більше корисних подій без втрати якості

1. **Почати з DOU + йой!, потім lviv.travel та Артсвіт.** Для цих джерел підтверджені
   майбутні зустрічі/програми поза основною концертною афішею. Для Харкова — YermilovCentre,
   для спорту — Run Ukraine. Одеський календар спочатку виправити на рівні трактування даних.
2. **Підтримати iCal коректно.** Читати VEVENT окремо від VTIMEZONE, розгортати folded lines,
   розрізняти DATE і DATE-TIME, floating time і TZID. За потреби серій — RRULE, EXDATE,
   RECURRENCE-ID та обмежений горизонт. Календарні UID корисні, але не гарантують сталості:
   музей включає часові числа у UID. Невідомий час не замінювати північчю.
3. **Розділити тривалу виставку та конкретний сеанс.** endDate визначає період актуальності,
   години роботи — доступність. Для серій потрібні окремі підтверджені дати. У поточному
   normalize дата без часу повертає None: DOU без доповнення буде відкинутий, не виправлений.
4. **Повний обхід і чесний звіт покриття.** Поточний harvest читає одну listing URL і
   до max_details карток. Додати пагінацію з visited URLs, max_pages, явною причиною
   зупинки та статусом `complete/partial/unknown`. Не обіцяти повноти на підставі HTTP 200.
5. **HTTP-кеш.** fetch підтримує ETag/Last-Modified, але harvest зараз не передає ці
   валідатори та не зберігає body. Потрібен кеш URL + тіло + валідатори + час перевірки;
   304 має повторно використати збережене тіло, а не дати порожній список.

## Як вимірювати наступний результат

Для кожної пари джерело × місто рахувати: знайдені сеанси, майбутні/триваючі, явні скасування,
підтверджені координати, невідомий час, приховані адреси, дублікати, нові унікальні live-події,
помилки та повноту обходу. Окремо дивитися найближчі 7/30 днів і категорії. Виграш — приріст
унікальних актуальних подій після злиття, а не кількість доменів у реєстрі.

Приймальні сценарії для майбутніх змін: повтор SQL не створює дублів; перенос зберігає ID;
одна скасована дата не скасовує всю серію; partial run не знімає події; online не отримує
координати офісу; city-only location не стає точною адресою; community-подія за межами
п’яти міст залишається доступною.

у цьому дослідницькому продовженні не ввімкнено; production SQL не застосовувався.
