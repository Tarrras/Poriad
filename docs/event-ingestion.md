# Наповнення подіями із зовнішніх джерел

Дата: 2026-09-07. Статус: проєкт фічі, не реалізовано. Ринкове обґрунтування — [market-and-launch.md](market-and-launch.md).

> **Перевірено на практиці.** Джерела виміряно скриптом `tools/probe_event_sources.py`; результати й поправки до цього документа — у [event-discovery.md](event-discovery.md). Три з них суттєві: жодне джерело не віддає координат; сторінки-списки несуть повний JSON-LD, тож обхід sitemap здебільшого зайвий; `guide.kyivcity.gov.ua` розмітки не має і до рівня B не належить.

## 0. Задача

Мапа не має бути порожньою в місті, де ще немає жодного нашого організатора. Потрібен конвеєр, який знаходить події в зовнішніх джерелах, приводить їх до нашої моделі, прибирає дублікати й публікує — без ручної роботи на кожну подію і без перетворення застосунку на ще одну афішу.

## 1. Головне рішення: два роди подій

Найважливіше в цій фічі — не парсер, а межа в моделі даних.

| | `community` | `listing` |
|---|---|---|
| Хто створив | користувач | конвеєр імпорту |
| Приєднання, місткість, черга | так | **ні** |
| Дії користувача | приєднатися, зберегти, поділитися | зберегти, поділитися, «купити квиток» (вихід на джерело), «зібрати компанію» |
| Фото, редагування | організатор | заборонено |
| Вага в ранжуванні | 1.0 | 0.75 |
| Бейдж | категорія | «Афіша · <джерело>» |

Спроба зробити імпортовані події «приєднуваними» ламає весь сенс `capacity` й черги: ми не знаємо місткості чужого концерту й не можемо нею керувати. Натомість `listing` отримує власну дію — **«зібрати компанію»**: створює прикріплену `community`-подію («зустрічаємось о 18:00 біля входу»), яка вже має нормальну місткість. Так афіша стає джерелом спільнотних подій, а не їхнім замінником.

Ці файли треба перечитувати щоразу перед обходом, а не покладатися на цей знімок.

## 3. Схема даних

```sql
-- Джерела та їхні правила обходу.
create table public.event_sources (
  id uuid primary key default gen_random_uuid(),
  slug text not null unique,
  name text not null,                       -- показуємо як «Афіша · <name>»
  kind text not null check (kind in ('ics','jsonld','sitemap_jsonld','api','rss','telegram','manual')),
  base_url text not null,
  city text,
  organizer_id uuid not null references public.profiles(id),  -- синтетичний профіль джерела
  weight numeric not null default 0.5 check (weight between 0 and 1),
  crawl_delay_seconds integer not null default 5,
  licence text,                             -- на якій підставі беремо: 'partner' | 'jsonld_public' | 'agreed'
  enabled boolean not null default false,
  etag text, last_modified text, last_run_at timestamptz
);

alter table public.events
  add column origin text not null default 'community'
      check (origin in ('community','import','partner')),
  add column source_id uuid references public.event_sources(id),
  add column source_uid text,               -- стабільний ідентифікатор у джерелі
  add column canonical_url text check (canonical_url is null or canonical_url like 'https://%'),
  add column content_hash text,             -- виявлення змін без повторного парсингу
  add column dedupe_key text,               -- ключ блокування, розділ 5
  add column quality numeric,               -- 0..1, розділ 6
  add column import_status text check (import_status in ('live','stale','withdrawn')),
  add column price_min numeric, add column is_free boolean;

create unique index events_source_uid_uidx
  on public.events(source_id, source_uid) where source_id is not null;

-- Кеш геокодування: один театр геокодується один раз, а не 200.
create table public.venues (
  id uuid primary key default gen_random_uuid(),
  norm_name text not null, norm_address text not null,
  latitude double precision not null, longitude double precision not null,
  city text, confidence numeric, geocoded_at timestamptz not null default now(),
  unique (norm_name, norm_address)
);

-- Сире й проміжне живе поза public: користувачам це бачити нема чого.
create table private.ingest_items (
  id uuid primary key default gen_random_uuid(),
  run_id uuid not null, source_id uuid not null references public.event_sources(id),
  source_uid text not null, url text, raw jsonb not null, content_hash text,
  stage text not null,                       -- fetched|parsed|normalized|geocoded|deduped|published|rejected|review
  reject_reason text, candidate_event_id uuid, similarity numeric,
  created_at timestamptz not null default now()
);
create table private.ingest_runs (
  id uuid primary key default gen_random_uuid(), source_id uuid not null,
  started_at timestamptz not null default now(), finished_at timestamptz,
  fetched int default 0, parsed int default 0, geocoded int default 0,
  published int default 0, merged int default 0, rejected int default 0, review int default 0,
  error text
);
```

Два зауваження до наявної схеми. По-перше, `events.organizer_id` — `not null` із зовнішнім ключем на `profiles`, тому кожне джерело отримує **синтетичний профіль** («Афіша Києва · moemisto»); нічого в RLS міняти не треба. По-друге, `image_url` уже має `CHECK (like 'https://%')` — імпортована обкладинка або лишається посиланням на джерело, або не існує; перекладати чужі зображення в наш Storage можна лише за домовленістю, і бакет усе одно перевіряє належність події.

## 4. Конвеєр

Вісім ідемпотентних стадій. Кожна читає й пише `private.ingest_items`, тому перезапуск із середини безпечний. Виконання — Supabase Edge Function на розкладі (`pg_cron`), одна функція на стадію або одна на джерело з внутрішнім циклом.

```
S0 discover → S1 fetch → S2 extract → S3 normalize → S4 geocode
   → S5 dedupe → S6 classify+score → S7 publish/retire
```

**S0 discover.** Головний режим — `listing_jsonld`: сторінка-список за містом, яка вже несе повний JSON-LD (три запити на добу покривають Київ; див. [event-discovery.md](event-discovery.md), розділ 1.2). `ics` — сам фід. `sitemap_jsonld` лишається для добору й **обов'язково** фільтрується за `lastmod` > `last_run_at`: у `moemisto.ua` лише 4% із 12 862 URL стосуються поточного року. Перед усім — читання `robots.txt` і застосування `Crawl-delay`.

**S1 fetch.** Умовний GET (`If-None-Match`/`If-Modified-Since`). 304 → пропуск без витрат. Інакше — `content_hash = sha256(нормалізоване тіло)`; якщо хеш збігся з наявним, стадії S2–S6 пропускаються повністю. Ліміт швидкості на джерело, експоненційний backoff на 429/5xx.

**S2 extract.** Драбина пріоритетів, зверху вниз, перший успіх виграє:
1. `VEVENT` з ICS (`SUMMARY`, `DTSTART`, `DTEND`, `LOCATION`, `GEO`, `URL`, `UID`);
2. JSON-LD `Event`/`MusicEvent`/`TheaterEvent` → `name`, `startDate`, `endDate`, `location.address`, `location.geo`, `offers.price`, `image`, `url`;
3. мікророзмітка / RSS;
4. LLM-екстракція з очищеного тексту в **строгу JSON-схему** з полем `confidence`.

LLM ніколи не викликається, якщо є структуровані дані: це і дорожче, і нестабільніше. `source_uid` = `UID` для ICS, інакше канонічний URL.

**S3 normalize.** Тут гине більшість сміття, і саме тут потрібні реальні дрібниці, видимі в даних: розгортання HTML-сутностей (`&laquo;`, `&nbsp;`), прибирання `\r\n`, обрізання заголовка під наш `CHECK` (3..120) без обриву посеред слова, опис — під 5000. Якщо `endDate` немає (звична річ), тривалість береться за замовчуванням із категорії: концерт 3 год, вистава 2 год, лекція 2 год, спорт 1.5 год. Ціна з `offers` → `price_min`, `is_free = (price_min = 0 або offers відсутні й у тексті є «безкоштовно»/«вхід вільний»)`. `time_zone` — з геоточки, не з нашого пристрою. **Зсуву в даних джерела довіряти не можна:** `moemisto.ua` позначає локальний київський час як `+0000` (12 із 12 сторінок вибірки), тож джерело має властивість `tz_policy = 'force_local'`, а не поправку в парсері.

**S3a. Що подією не є.** Джерела продають квитком і постійні атракціони: «Київський океанаріум», «Музей медуз», VR-екскурсію, майстер-клас із кінцем через 560 днів. У них `endDate` — не кінець події, а дата, доки діє квиткова пропозиція. Запис, що триває довше за `pipeline.PERMANENT_RUN` (90 днів), відсікається тут і в базу не потрапляє: фільтр на показі сховав би рядок, але рядок лишився б і спливав у кожному новому запиті. Межа евристична — у вибірці на п'ять міст реальний прокат виставок укладався в 86 днів, а найкоротша постійна пропозиція починалась зі 111; це підібрано на одній вибірці, а не виміряно. Подія, що вже почалась, але ще триває, при цьому лишається: її показ описано в [../supabase/README.md](../supabase/README.md), розділ «Події, що вже тривають».

**S4 geocode.** Спершу `venues` за `(norm_name, norm_address)`. Промах — `GeoSearchRepository` (Photon, уже в стеку), результат кешується. Точка поза межами bbox міста або з низькою впевненістю → `review`, не в мапу. Це найдешевший фільтр якості з усіх: подія без точного місця для гео-first застосунку не існує.

**S5 dedupe.** Розділ 5.

**S6 classify + score.** Розділ 6.

**S7 publish/retire.** `upsert` у `events` за `(source_id, source_uid)`, з `origin='import'`, `import_status='live'`. Подія, якої не було в N останніх запусках, або чий URL віддає 404 → `import_status='withdrawn'` і зникає з видачі. **Не видаляємо**: її могли зберегти, і збережений порожній запис гірший за позначку «більше не проводиться».

## 5. Дедуплікація

Один концерт трапляється в `concert.ua`, `karabas.com` і в Telegram-каналі. Три піни в одній точці — це не каталог, це поломка.

**Фаза 1 — блокування.** Порівнювати всі з усіма не треба. Ключ:

```
dedupe_key = date_local || ':' || round(lat,2) || ',' || round(lng,2)
```

(≈1.1 км сітка). Кандидати добираються ще й за триграмним індексом заголовка — `pg_trgm` уже дає `similarity()` і GIN-індекс, окрема пошукова система не потрібна.

**Фаза 2 — оцінка.**

```
score = 0.45·titleSim + 0.25·timeProx + 0.20·geoProx + 0.10·venueSim
```

- `titleSim` — на нормалізованих заголовках: нижній регістр, зняття пунктуації, викид загальних слів («концерт», «вистава», «квитки», «шоу»), транслітерація для порівняння укр/рос написань. `similarity()` з `pg_trgm`.
- `timeProx` — 1.0 при |Δ| ≤ 15 хв, лінійно до 0 на 3 год. **Поріг навмисно вузький:** у джерелах трапляються сеанси «6 вересня об 11.00 і 13.00» — це дві різні події, злити їх було б помилкою.
- `geoProx` — 1.0 при ≤100 м, 0 при ≥1 км.
- `venueSim` — схожість нормалізованих назв майданчиків.

**Рішення.**

| score | Дія |
|---|---|
| ≥ 0.86 | Автоматичне злиття. Канонічною лишається подія з джерела з вищим `weight`; друга стає рядком у `event_aliases` зі своїм `canonical_url` (щоб кнопка «купити квиток» вела на обидві платформи) |
| 0.70 – 0.86 | Черга ручного перегляду (`stage='review'`). Не публікується |
| < 0.70 | Різні події |

**Окремий випадок — імпорт проти спільнотної події.** Якщо користувацька подія збігається з імпортованою, **зливати не можна ніколи**: у користувацької є місткість, черга й організатор. Замість злиття — продуктова підказка при створенні: «Схоже, ви йдете на *Х*. Прикріпити вашу зустріч до цієї події?» Це той самий місток афіша→спільнота з розділу 1.

## 6. Класифікація та якість

**Категорія** (наші сім: `music, sport, art, food, games, outdoors, social`) — правила спершу, модель потім:
1. `@type` зі schema.org: `MusicEvent`→`music`, `TheaterEvent`/`ExhibitionEvent`→`art`, `SportsEvent`→`sport`, `FoodEvent`→`food`;
2. лексикон ключових слів по заголовку й майданчику, українською й російською (театр, галерея, вернісаж, забіг, майстерклас, дегустація, настолки, квіз…);
3. лише для решти — LLM з фіксованим списком із семи міток, результат кешується за `content_hash`.

**Оцінка якості** `quality ∈ [0,1]`, зважена сума: є геоточка з високою впевненістю (0.30), є час початку й кінця (0.15), опис ≥120 символів (0.15), є зображення (0.10), вага джерела (0.20), не є частиною серії з >20 однакових сеансів (0.10). На мапу потрапляє лише `quality ≥ 0.55`; решта зберігається, але прихована — так поріг можна переглянути без повторного обходу.

**Ранжування у видачі.** Імпорт не має витісняти спільноту:

```
final = tasteScore(event) · (origin = 'community' ? 1.0 : 0.75) · quality
```

Головна вкладка й карусель мапи спершу показують `community`, «Афіша» — окремою секцією.

## 7. Захисні запобіжники

- Імпортовану подію не можна редагувати, приєднатися до неї, вивантажити до неї фото. Це фіксується в RLS і в RPC приєднання, а не в клієнті — інакше правило тримається лише до першого пропатченого застосунку.
- Ліміт публікацій на джерело за запуск (напр. 300). Перевищення — зупинка й помітка запуску.
- Скарга на імпортовану подію ставить на паузу **всю партію** цього джерела до перегляду людиною.
- Кожен рядок несе `ingest_run_id`, тож один поганий запуск відкочується цілком: `update events set import_status='withdrawn', ingest_run_id=null where source_id=… and ingest_run_id=…` (з `null` — інакше наступний дамп поверне рядки, див. нижче).
- Спостережуваність — наявними тегами `PoruchLog` (`http`, `discovery`) плюс новий `ingest`, і лічильники в `ingest_runs`. У лог не потрапляє тіло сторінки — лише джерело, лічильники й час.

### Ручне зняття: що переживає наступний дамп

Дамп (`tools/ingest/emit.py`) поводиться так:

- **Вимкнене джерело не пишеться.** `insert … select … join event_sources … where enabled`: подій джерела з `enabled=false` дамп не вставляє й не оновлює, тож знятими вони й лишаються.
- **Ручне зняття — це `withdrawn` з `ingest_run_id is null`.** Такий рядок upsert не повертає в `live`, навіть якщо подія знову в афіші. Автоматичні зняття (скасування з джерела, зникнення з афіші, дубль) завжди ставлять `ingest_run_id` поточного прогону, тож коли подія повертається в афішу, наступний дамп знову робить її `live`. Окремого стовпця для ознаки немає: `null` у `ingest_run_id` імпортованого рядка інакше не буває.
- `stale` (завершені) дамп теж повертає в `live`, якщо джерело перенесло подію.

Зняти джерело повністю (opt-out, розділ 8, пункт 7):

```sql
update public.event_sources set enabled=false where slug='<slug>';
update public.events set import_status='withdrawn', ingest_run_id=null, updated_at=now()
where source_id=(select id from public.event_sources where slug='<slug>') and import_status<>'withdrawn';
```

Друга команда з `ingest_run_id=null`, щоб зняття пережило й повторне ввімкнення джерела. Також прибрати або вимкнути джерело в `tools/ingest/sources.py`, щоб обхід сайту припинився, а не лише запис.

Зняти одну подію: та сама друга команда з `where id='<uuid>'`. Повернути — `set import_status='live', ingest_run_id=null`; наступний дамп проставить свій run_id.

### Моніторинг прогону

Розкладу поки немає: обхід запускається руками. Запускати завжди з `--report` за тим самим шляхом (напр. `out/run.json`) — минулий звіт з цього файла служить базою для порівняння. Код виходу `1` — хоча б одне джерело з `error`; такий SQL не застосовувати, доки не зрозуміло, що сталося. Наприкінці stderr перелічує `ПОМИЛКА ДЖЕРЕЛА місто · slug: …`. У звіті (`sources[]`, запис на пару місто/джерело) дивитись:

| Поле | Що означає |
| --- | --- |
| `error: NO_EVENTS…` | сторінка без JSON-LD: зміна розмітки або блокування |
| `error: NO_USABLE_EVENTS…` | розмітка є (`parsed` > 0), а придатних 0 — «тихий нуль», майже завжди зміна верстки |
| `error: SHARP_DROP…` | придатних (`items`) менше 30% від минулого звіту (для джерел, що мали ≥10) |
| `error: HTTP …`, `PARTIAL_DETAILS`, `catalog_errors` | мережа, robots.txt, 413 (відповідь понад 10 МБ) або частина карток не відкрилась |
| `bad_events` | окремі події, пропущені через виняток у розборі чи незаписувані поля (задовгі, `UNWRITABLE` у `reject_reason`); дамп без них цілий |
| `items`, `published`, `review`, `rejected` + `reasons` | обсяги; різке зростання `review` — зламані пороги чи геокодування |
| `retire` | чи дозволено знімати зниклі з афіші (`так` або причина відмови) |

## 8. Право й етика

Це не юридична консультація, а робочі межі, яких варто триматись до перевірки юристом.

1. **Пріоритет домовленості.** Рівень A (партнерський ICS) не має жодного з наведених нижче ризиків. Кожне джерело рівня B варто спробувати перевести в A одним листом — більшість афіш зацікавлені в додатковому трафіку.
2. **Факти, а не текст.** Дата, час, місце, ціна — факти, вони не охороняються авторським правом. Опис події — охороняється. Тому зберігаємо й показуємо **до ~200 символів** із явним «Читати повністю на джерелі» і `canonical_url`. Повний опис із джерела в базу не кладемо.
3. **Атрибуція обов'язкова й видима**: «Афіша · <джерело>» на картці й посилання на першоджерело в деталях.
4. **`robots.txt` і `Crawl-delay` виконуються буквально**, з власним User-Agent із контактною адресою.
5. **Зображення** — посиланням на джерело; копіювати в Storage лише за домовленістю.
6. **Персональні дані не імпортуються.** Імена організаторів із чужих сайтів у профілі не заводяться; організатор імпортованої події — синтетичний профіль джерела.
7. **Opt-out за один лист.** Джерело просить прибрати — `enabled=false` і `withdrawn` для всієї партії, того ж дня (SQL — розділ 7, «Ручне зняття»). Адреса для листів — `hello@poriad.app`, її й сторінку https://poriad.app/bot називає User-Agent `PoriadBot`.
8. **Telegram — лише за згодою каналу.** Взаємна вигода очевидна (ми даємо мапу й посилання назад), але без згоди не починаємо.

## 9. Черга ручного перегляду

Не потрібен окремий адмін-застосунок: `private.ingest_items` зі `stage='review'` переглядається у Supabase Studio, а рішення — двома SQL-функціями (`private.ingest_approve(item_id)`, `private.ingest_reject(item_id, reason)`). Обсяг черги — сама по собі метрика: якщо в неї падає >15% елементів, зламані пороги, а не джерело.

## 10. Етапи

| Етап | Обсяг | Оцінка | Що доводить |
|---|---|---|---|
| **0** | Ручний імпорт ICS/CSV для 3 партнерських локацій + `origin`/`listing` у моделі та UI | 2–3 дні | Межа `community`/`listing` тримається в UI й RLS. Нуль юридичного ризику |
| **1** | Sitemap+JSON-LD обхідник для `moemisto.ua` та `concert.ua`, геокеш, дедуплікація, черга перегляду | ~1 тиждень | Мапа Києва наповнена до запуску (ціль ≥200 подій/міс) |
| **2** | Дія «зібрати компанію» та «Це моя подія» (claim) на `listing`-подіях | 3–4 дні | Афіша конвертується в спільнотні події й в організаторів — головна стратегічна ставка |
| **3** | Telegram-джерела з LLM-екстракцією, за згодою каналів | ~1 тиждень | Доступ до реальної української пропозиції малих подій |
| **4** | Зворотний фід: `poruch.app/e/{id}` зі schema.org розміткою + власний ICS | 3–4 дні | SEO-канал із розділу 5 і симетрія: ми теж стаємо джерелом |

Етап 2 важливіший за етап 3, хоч і виглядає меншим: він перетворює імпорт із декорації на воронку.
