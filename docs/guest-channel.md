# Серверний канал повернення для гостя

Стан на 2026-10-20. Варіант А реалізовано: міграція `20261030140000_guest_winback` (на dev застосована
ще під старим номером `20261021140000`) і функція `push` — на dev (`supabase/tests/winback.sql` — PASS), клієнт — у коді обох платформ, у сторах ще нема; prod — ні. Відкриті питання
2–4 взято за пропозиціями нижче, питання 1 чекає власника акаунтів сторів (`store/listing.md`). Продовжує
[бриф утримання](retention-brief-2026-10.md), §8 п. 6.

## Проблема

Сервер не знає про гостя нічого: `push_tokens.user_id not null`, `PushSync.register()` виходить без акаунта.
Тож він не може:

1. **Надіслати свіже.** Локальна драбина дайджестів (a41ff09) — це 4 п'ятниці зі знімка останнього відкриття. Після
   28-го дня — тиша, хоч в афіші щотижня з'являються нові події.
2. **Знати, хто спить.** Стани з брифу §9 (активний / під ризиком / сплячий / відпалий) рахувати нема з чого: дата
   останнього відкриття живе лише на телефоні. Amplitude бачить сесії, але не дає ні SQL, ні дії.
3. **Порівняти з контрольною групою.** Локальне сповіщення не має «не надсилати 20%» з обліком на сервері.

Чого серверний канал **не** розв'язує: людину без дозволу на сповіщення. Будь-яке сповіщення, локальне чи серверне,
проходить через дозвіл системи. Цю частину закрили провізорний дозвіл iOS і питання в першій сесії на Android 13+
(кроки 1–2 брифу).

## Цілі

1. Пристрій із дозволом, з якого не відкривали застосунок ≥28 днів, отримує **не більше двох** пушів зі свіжими
   подіями свого міста — близько 30-го і 60-го дня, у п'ятницю о 17:00. Далі — тиша до наступного відкриття.
2. Сервер знає `last_seen` кожного пристрою, з гостем чи з акаунтом. Стани §9 — одним SQL.
3. 20% придатних пристроїв — контрольна група без пушів, з обліком, щоб порівняти повернення.

## Не цілі

- Збереження й «Стежити» для гостя — це варіант Б нижче, окреме рішення.
- Email, SMS, нові дозволи.
- Зміна локальної драбини: вона лишається на тижні 1–4, сервер бере 5-й і далі.

## Варіанти

| | А. Пристрій без акаунта | Б. Анонімні акаунти Supabase | В. Довша локальна драбина (8 п'ятниць) |
|---|---|---|---|
| Що дає | Свіжі події після 28-го дня, `last_seen`, контрольна група | Усе з А + збережені, «Стежити», «Шукаю компанію» для гостя без входу | Ще 4 п'ятниці зі старого знімка |
| Вартість | M: міграція, гілка у функції `push`, виклик у `PushSync`, політика | L: увімкнути вхід і Turnstile, аудит 99 RPC і 17 політик на `is_anonymous`, прив'язка Apple/Google за ID-токеном у власному `ApiClient`, злиття даних при вході в наявний акаунт, чистка анонімів, фільтр у всіх SQL-метриках | S: одна константа |
| Ризики | Спам рядками через публічний ключ — дешевий (див. «Зловживання») | Анонім із роллю `authenticated` пройде будь-яку політику, яку забули звузити: створення подій, чат, скарги | Нічого не міряє; концерти через 2 місяці в знімку є, свіжих подій нема |

**Рекомендація: А зараз.** Б — коли дані покажуть попит: `auth_wall` з новим параметром `action` (нижче) скаже, скільки
гостей вперлись саме в «Зберегти» чи «Стежити». В — ні: без вимірювання ми не дізнаємось, чи це повертає, а міряти —
половина мети. А не заважає Б: таблиця пристроїв лишиться й з анонімними акаунтами.

## Дизайн варіанта А

### Дані

```sql
create table private.devices (
  token text primary key,               -- APNs (64 hex) або FCM; той самий, що в push_tokens
  platform text not null check (platform in ('android','ios')),
  city text,                            -- з HomeLocation, null — своє місце на мапі
  interests text[] not null default '{}', -- ключі EventCategory з Taste.interests
  last_seen timestamptz not null default now(),
  created_at timestamptz not null default now()
);
create table private.winback_sends (
  token text not null references private.devices(token) on delete cascade,
  step smallint not null check (step in (1, 2)),
  holdout boolean not null,             -- true — не надсилали, лише облік контрольної групи
  sent_at timestamptz not null default now()
);
```

Без `user_id` свідомо: як і аналітика, пристрій не зв'язаний з акаунтом (обіцянка політики). Акаунтні пуші так і
йдуть через `push_tokens`.

RPC для `anon` і `authenticated`:

- `touch_device(p_token, p_platform, p_city, p_interests)` — upsert, `last_seen = now()`. Перевірки: формат токена
  (APNs — `^[0-9a-f]{64}$`, FCM — `^[A-Za-z0-9_:-]{100,4096}$`), платформа, місто з п'яти відомих або null,
  інтереси — лише відомі ключі, не більше 11.
- `forget_device(p_token)` — видаляє рядок. Клієнт кличе, коли людина вимкнула дайджест у профілі або дозволу нема.

### Клієнт (спільний код)

- `PushSync`: окрім `register()` під акаунтом — `touch()` для будь-кого, коли є токен **і** дозвіл (authorized чи
  provisional) **і** `device:digest` увімкнено. Інакше — `forget()`. Не частіше разу на 12 годин (мітка часу в
  сховищі пристрою), плюс одразу після зміни міста, інтересів чи перемикача дайджесту.
- Відкриття пушу: `push_open` з `reason = winback` і `step` (1 | 2). Словник у `docs/analytics.md`.
- `auth_wall` отримує `action`: `save`, `follow`, `join`, `create`, `companion` — дані для рішення про Б.

### Сервер

- `private.winback_due()` — пристрої з `last_seen` між 35 і 28 днями тому (крок 1) або між 63 і 56 (крок 2), для
  яких цього кроку ще не було після `last_seen`. Повернувся й знову заснув — драбина починається заново.
- Контрольна група — детерміновано: `abs(hashtext(token)) % 5 = 0`. Таким пише `winback_sends` з `holdout = true` і
  нічого не шле.
- Вміст — як локальний дайджест (`DigestRules`): події міста на найближчі суботу-неділю, спершу з інтересів людини;
  менше 3 — пропускаємо цю п'ятницю (крок не зараховано, і контрольній групі теж). Дві назви + кількість. Вікно
  кроку — 7 днів, тобто рівно одна п'ятниця: пропущений крок не повторюється, наступний — у своєму вікні. Так само
  зі збоєм розкладу в п'ятницю. Якщо це стане проблемою — розширити вікно кроку 1 до 28–49 днів.
- Розклад: pg_cron щогодини в п'ятницю (`12 * * * 5`; :02, :05 і :07 уже зайняті зведеннями й чергою тихих годин),
  функція сама перевіряє 17-ту годину за Києвом — так перехід на зимовий час не зсуває пуш.
- Доставка: `private.send_winbacks()` → `private.notify_push({type: 'winback', token, platform, step, city, total, titles})` → функція `push` шле прямо на
  токен, без пошуку людини. Мертвий токен (APNs 410, FCM UNREGISTERED) — видалити з `private.devices` так само, як із
  `push_tokens` зараз (`index.ts`, рядок 83).
- Чистка: рядки з `last_seen` старше 120 днів — видаляти тією ж задачею.

### Тексти

Без «ми сумуємо» і без «давно не заходили» (бриф, «Свідомо не робити»). Ті самі шаблони, що в локальної драбини
(`Copy.digest_title*`, `digest_more`), щоб людина впізнавала один голос; сервер тримає їх копію у функції `push`:

- Крок 1: заголовок як `digest_title` — «Київ: 40 подій на вихідних»; текст як `digest_more` — «Імпровізаційне шоу
  «Королі Крінжу», Червона Шапочка та ще 38».
- Крок 2: заголовок як `digest_title_3` — «Є куди на вихідних. Київ: 40 подій»; текст — той самий шаблон.

Назви подій у пушах — сирі, як у решті пушів і календаря (`displayTitle` лише в інтерфейсі).

### Зловживання

`touch_device` відкритий для публічного ключа, тож будь-хто може насипати рядків. Чим це загрожує: рядками в
таблиці й пушами на неіснуючі токени, які APNs і FCM відкинуть, а ми видалимо. Обмеження: перевірка формату, жорстка
стеля 100 000 рядків (вище — `touch_device` мовчки нічого не пише й пише в журнал), чистка за 120 днів. CAPTCHA не
потрібна — на відміну від анонімного акаунта, пристрій не дає жодних прав.

### Приватність

Новий запис без акаунта: токен пристрою, місто, інтереси, час останнього відкриття. До релізу:
- `site/privacy*.html` — розділ про сповіщення: що зберігаємо, навіщо, 120 днів, видалення через перемикач дайджесту.
- `store/listing.md` і App Privacy / Data safety — звірити, чи токен пушу вимагає нової категорії (відкрите питання 1).

### Як міряти

```sql
-- Стани з брифу §9 по пристроях.
select case when last_seen > now() - interval '7 days' then 'активний'
            when last_seen > now() - interval '14 days' then 'під ризиком'
            when last_seen > now() - interval '30 days' then 'сплячий'
            else 'відпалий' end as state, count(*)
from private.devices group by 1 order by 1;

-- Повернення за 7 днів після кроку: надіслано проти контрольної групи.
select s.step, s.holdout, count(*) as devices,
       count(*) filter (where d.last_seen between s.sent_at and s.sent_at + interval '7 days') as returned
from private.winback_sends s join private.devices d using (token)
group by 1, 2 order by 1, 2;
```

Читати лише коли в кожній групі ≥200 пристроїв (10% проти 20% — бриф §9). До того — абсолютні числа.

### Тести

- SQL (`supabase/tests/winback.sql`, усе відкочується): межі вікон 28/35 і 56/63 днів; після кроку 2 — тиша;
  повернення скидає драбину; контрольна група стабільна для того самого токена й близька до 20% на 1 000 токенів;
  менше 3 подій — крок не зараховано; `touch_device` відкидає кривий токен, місто й інтереси; стеля рядків;
  `forget_device` видаляє.
- Спільний код: `touch` не частіше разу на 12 годин; без дозволу чи з вимкненим дайджестом — `forget`.

### Розгортання

1. Міграція й функція `push` — на dev, тести SQL на dev.
2. Клієнт — у наступну збірку обох платформ разом із політикою.
3. Prod: міграція й `functions deploy push` до виходу збірки — `touch_device` без клієнтів просто ніхто не кличе.
4. Перший крок 1 піде не раніше ніж через 28 днів після того, як збірка з `touch` з'явиться в людей.

## Відкриті питання

1. Чи вимагає токен пушу без акаунта нової позиції в App Privacy (Apple) і Data safety (Google)? Перевірити перед
   релізом; якщо так — це «Identifiers → Device ID», «App functionality», не зв'язано з особою.
2. Інтереси на сервер — чи лише місто? Без інтересів текст гірший, але даних менше. Пропозиція: надсилати — вони вже
   ідуть на сервер в акаунтів (`interestsOwner`).
3. 30-й і 60-й день — чи 21-й і 45-й? Почати з 30/60 (не перетинається з локальною драбиною), подивитись на перших
   даних.
4. Пристрої з акаунтом теж у драбині? Так: «сплячий» — властивість пристрою, а не входу. Акаунтні пуші («Стежити»)
   від цього не змінюються.
