
Для вкладених шляхів JSON створіть теку заздалегідь (`mkdir -p out`). Код завершення 1 означає
помилку/неповний результат хоча б одного джерела; придатні результати інших джерел залишаються
в SQL і JSON. `--report` містить деталі. Джерело читає до 100 карток на місто; досягнення межі
позначається як неповний результат. `--sql-max-bytes` враховує заголовки й транзакції; мінімум
4096 байтів. Якщо один запис не вміщується, генерація зупиняється з помилкою.

Для Karabas перевірка статусів увімкнена за замовчуванням. `--no-karabas-status` призначений
для ізольованої діагностики; звичайний SQL краще не готувати без цієї перевірки. Обхід статусів
обмежений трьома сторінками й завжди позначений як partial: відсутність у них не означає,
що подія чинна. Конфлікт між desktop/mobile копіями таблиці йде у review без SQL.

Адаптери Артсвіт, YermilovCentre та Run Ukraine є в коді, але джерела вимкнені в реєстрі:
поточні сторінки відповідно мають відносні дати/періоди без сеансів, блокуються штатною
robots-перевіркою або ще не підтверджують точний час стартів. Їх можна пробувати явно через
`--source`; неоднозначні записи не перетворюються на події опівночі.

SQL реєструє відсутні джерела через `ON CONFLICT DO NOTHING`. Потребує вже застосованих
міграцій проєкту. Використовуйте лише файли з відповідного `.manifest.json` у вказаному порядку;
не змішуйте частини різних запусків. Дампи/кеші та байткод лишаються поза Git.

Розділи нижче описують історію попередніх версій; наведені там кількості та старі правила
зняття/ідентифікації не є поточною специфікацією.

Наповнює мапу подіями з відкритих джерел, поки база власних організаторів порожня. Обґрунтування, перелік джерел і всі виміряні числа — [../../docs/event-discovery.md](../../docs/event-discovery.md).

## Запуск

```bash
python3 -m tools.ingest                    # УСІ міста, суха проба
python3 -m tools.ingest --sql-dir out/     # усі міста, SQL по файлу на місто
```

Без аргументів обходить усі міста, які вміють джерела — сьогодні пʼять. Це **суха проба**: друкує зведення й нічого не змінює. Конвеєр не має доступу до бази й не повинен його мати: обхід чужих сайтів і запис у власну базу різні за наслідками, і зводити їх в одну команду означає зробити необоротне таким же дешевим, як оборотне.

```bash
python3 -m tools.ingest --city Львів --sql out.sql    # одне місто, один файл
python3 -m tools.ingest --source karabas --json out.json
python3 -m tools.ingest --refresh-osm                 # перезавантажити дампи майданчиків
python3 -m tools.ingest --no-photon                   # без геокодування, лише OSM
python3 -m tools.ingest.test_ingest                   # тести пасток, без мережі
```

Міста беруться з самих джерел (`sources.py`), а не зі списку в коді: додав місто в `listing_urls` — воно обходиться. Місто без прямокутника в `geocode.CITY_BBOX` скрипт відхиляє одразу, а не після півгодинного обходу.

Залежностей немає — лише стандартна бібліотека.

## Що відбувається

```
сторінка-список → JSON-LD → нормалізація → майданчик з OSM → оцінка якості → SQL
```

Головне рішення: точка входу — **сторінка-список**, а не sitemap. Один запит до `kyiv.karabas.com` дає 147 подій, до `concert.ua/uk/kyiv` — 115. Обхід sitemap коштував би 12 862 запити заради меншого результату.

## Майданчики — вузьке місце

Жодне джерело не віддає координат. Їх дає дамп OpenStreetMap (~4 800 обʼєктів Києва одним запитом, ODbL), але автоматичне зіставлення за назвою бере лише частину: афіші пишуть «МЦКМ (Жовтневий палац)» там, де в OSM стоїть «Міжнародний центр культури і мистецтв».

Це виміряно прямо: **пʼять звірених вручну рядків у `aliases.json` підняли результат із 77 до 155 подій.** Незіставленими лишаються найбільші майданчики, тож година роботи тут вартує більше за будь-яке покращення автоматики.

Два зауваження до `aliases.json`:

- Для майданчиків, яких в OSM немає взагалі (`ORIGIN STAGE`, `COMEDY SHELTER`), значенням можуть бути прямі координати: `{"lat": 50.45, "lon": 30.52}`.
- **Координати вигадувати не можна.** «Клуб ATLAS» свідомо не зіставлений з «Atlas Coffee» — це різні заклади, і подія, тихо поставлена не на тому місці, гірша за подію в черзі перегляду. Тест `test_venue_matching` це закріплює.

## Куди це переїде

Конвеєр написано так, щоб логіка переносилась у Supabase Edge Function на розкладі `pg_cron` (розділ 4 `docs/event-ingestion.md`). Python тут тому, що його можна запустити й перевірити на живих даних сьогодні, а не тому, що це кінцева форма.

## Геокодер: чому він шукає тільки адресу

Photon (той самий інстанс, що в застосунку) стоїть третім щаблем після `aliases.json` і дампу OSM. У нього два запобіжники, і обидва з'явилися після того, як він помилився:

- **Ніколи не за назвою закладу.** На запит «ORIGIN STAGE, Київ» Photon упевнено віддає кам'яну стелу «Центр Русі» з `type=house` — тобто відповідь, яку фільтр за точністю пропускає, а вона поставила б 20 подій на випадковий пам'ятник. Метод називається `lookup_street` і назви закладів не приймає взагалі.
- **Тільки з номером будинку**, тільки рівень `house`/`street`, тільки в межах bbox міста.

Окремо варто знати: `lang=uk` Photon **не підтримує** (лише `default`, `de`, `en`, `fr`) і віддає HTTP 400. Колись це коштувало 206 запитів, які мовчки нічого не знайшли, бо помилка ковталася — тому `Geocoder.errors` тепер видно у виводі CLI.

## Зіставлення за входженням

Поріг схожості сам по собі не розрізняє правильні збіги від хибних:

```
«Київський Палац спорту» → «Палац спорту»   0.55  правильно
«Dorothy pub» → «Dorothy»                   0.64  правильно
«Feels Garden» → «Garden»                   0.50  ПОМИЛКА, інший заклад за 10 км
```

Поріг 0.6 відсік би помилку разом із «Палацом спорту», у якого 23 події. Розрізняє їх не score, а те, що хибний збіг — **одне загальне слово**, тому однослівна назва в OSM вимагає вищої впевненості. Це евристика на п'ятьох прикладах, а не закон: з новим джерелом її треба перевіряти заново.

## Часові пояси: одна вада на джерело, і всі різні

`event_sources.tz_policy` — не налаштування, а опис конкретної вади конкретного джерела.

| Політика | Джерело | Що робить |
|---|---|---|
| `source` | concert.ua | вірити зсуву як є |
| `force_local` | moemisto.ua | зсув `+0000` ігнорувати, цифри читати як київський час |
| `utc_is_local` | karabas.com | привести до UTC, а ці цифри прочитати як київський час |

karabas вартий окремої уваги, бо його вада **проходить будь-яку перевірку формату**: зсув коректний і навіть з правильним переходом на зимовий час. Але момент зсунуто вперед рівно на цей зсув — сторінка показує «17 жовтня 2026, 18:00», а JSON-LD каже `2026-10-17T21:00:00+03:00`.

Знайшлося це не перевіркою розмітки, а **дублікатами**: ДахаБраха, СКАЙ і FIЇNKA продаються і на karabas, і на concert.ua, і час розходився рівно на UTC-зсув. Тому дублікати між джерелами — не сміття, яке треба мовчки зливати, а найдешевший детектор систематичних вад.

Друга дешева перевірка — **гістограма годин початку**. Після поправки: пік о 18:00–19:00 (110 подій зі 176). До поправки пік стояв на 21:00–22:00, що для Києва з комендантською годиною неможливо. Варто дивитись на неї після підключення кожного джерела:

```sql
select extract(hour from starts_at at time zone 'Europe/Kyiv')::int as година, count(*)
from public.events where origin='import' group by 1 order by 1;
```

## Стоси на мапі: наслідок кеша майданчиків

Кеш дає всім подіям одного закладу **однакові** координати — у цьому й був сенс. Але на мапі це
означає, що 176 київських подій стоять на 34 точках, у найбільшій — 32 (МЦКМ). Такі піни не
розходяться за жодного зуму, тож тап завжди відкривав ту саму подію, а решта стосу була недосяжна:
дев'ять подій із десяти.

**Перебудовано (2026-09-07): пін = заклад, не подія.** Групування живе в спільному домені
(`MapPins.group`), тож Android та iOS показують ту саму мапу. Пін несе категорію найближчої події,
підпис із кількістю подій, і список `ids` — тап читає його з самої фічі, а не вигрібає з рендерера.
Кластери тепер сумують **події**, а не місця (`clusterProperty`/`clusterProperties`).

Результат на київських даних: **34 піни замість 168**, тап у заклад одразу відкриває всі його події
(«Тут подій: 15»), без пробивання крізь кластери. Кластер, який наближення не розділить, теж
розкривається списком замість безкінечного зуму.

## Дублікати між джерелами

Той самий концерт продають і karabas, і concert.ua — у київській вибірці таких 7 зі 176 (4%).
`drop_cross_source_duplicates` лишає копію з джерела з вищою вагою (`concert.ua` 0.8 > `karabas`
0.7), решту позначає `stage='duplicate'`.

Правило навмисно обережне: місце й момент мають збігатися **точно**, а назви порівнюються як
множини значущих слів на входження («Ніно Катамадзе» ⊂ «Ніно Катамадзе. Премʼєра нового альбому»).

Причина обережності — конкретна: у MODI о 19:00 того самого дня йдуть «Відео-галерея» і
«Відкритий клуб». Це різні події на одній точці, і хибне злиття сховало б одну назавжди. Тест
`test_dedupe` закріплює саме цей випадок, а не лише щасливий шлях.

## Три вади, знайдені й полагоджені дорогою

**Дедуплікація виконувалась після генерації SQL.** `emit.events_sql` фільтрує за `stage ==
"published"` у момент виклику, а `drop_cross_source_duplicates` бігло вже після циклу по джерелах.
Тобто дублі, про які підсумок рапортував «злито», лежали у файлі. Тепер порядок: зібрати все →
дедуплікувати → аж тоді генерувати SQL.

**Запит до Overpass не працював поза Києвом.** Стояло `area["name"=<місто>]["admin_level"="4"]`.
Рівень 4 — це область; для Києва збігається лише через спецстатус. Для решти запит повертав
**нуль обʼєктів, а не помилку** — індекс мовчки виходив порожній. Тепер запит іде за
прямокутником із `geocode.CITY_BBOX`: він усе одно потрібен геокодеру, тож джерело правди одне,
і місто без прямокутника кричить, а не мовчить. Заодно додано перебір дзеркал Overpass і відмову
кешувати порожній дамп — та сама вада заходила через ці двері.

**Розбіжність координат між джерелами.** `same_event` вимагає побітової рівності широти й
довготи. Якщо два джерела дійшли до координат різними щаблями драбини — одне через індекс OSM,
друге через Photon, — точки розходяться на десятки метрів, дубль не зливається, і `MapPins` теж
не зводить його в один пін. Користувач бачить ту саму подію двічі поруч.

Для цього є `pipeline.near_miss_pairs`: вона нічого не змінює, лише друкує пари, схожі на дублі,
але з різними координатами. Її вивід — це готовий список робіт для `aliases.json`. На реальних
даних вона знайшла 1 пару в Києві, 5 у Львові, 10 у Дніпрі; після псевдонімів лишилась 1 (Malevich
Concert Arena, якої немає в OSM і яка потребує координат від людини).

## Категорія `comedy`

Стендап виділено з `art` у власну категорію. Причина не таксономічна, а продуктова: це та
пропозиція, на яку ходить цільова аудиторія 22–35, і в спільній скриньці з ляльковим театром вона
губиться. Ціна: міграція (CHECK на `events.category` і на `user_preferences.categories`), спільний
`Rules.categories`, три мапи кольорів і мітка на кожному клієнті, значок у
`tools/generate_icons.py` — звідти він генерується одразу для Kotlin і Swift.

`_BY_TYPE` тепер шле `ComedyEvent → comedy`, а лексикон ловить нетипізовані («відкритий мікрофон»).
Заодно `ChildrensEvent` переїхав із `social` до `art`: дитячі вистави розводили одну з категорій
вістря, порожнеча яких і є стратегічною проблемою.

## Рівень C виміряно й відхилено

Перевірено `kontramarka`, `ticketsbox`, `ticket.kiev.ua`, `tickets.ua` за правилом «спершу шукати
вбудований JSON, а не припускати HTML-парсинг». Жодна не має корисного блоку даних, і — головне —
**у жодної не видно вуличних адрес із номером**. Без них `geocode.lookup_street` відмовляє, тобто
джерело не дало б координат і лише наповнювало б чергу перегляду. Будувати парсери під них зараз
немає підстав.

## Чи вистачає категорій: скрипт питає це сам

Найтихіша вада класифікатора — його останній рядок. `normalize.classify` **завжди** повертає
категорію: не розпізнав — віддав `social`. Тому подія, для якої скриньки немає, виглядає точно як
розпізнана, і прогалину видно лише випадково. Саме так стендап місяцями лежав у `art`.

`report.category_gaps` робить це видимим, і в ньому два сигнали різної сили.

**Головний — типи schema.org усередині кошика.** Якщо в одній категорії живуть кілька різних
типів і чужий займає помітну частку, це рівно та ситуація, у якій був стендап:

```
art    TheaterEvent 494 (81%), ChildrensEvent 91 (15%), Event 11 (2%)
       ← ChildrensEvent: 91 подій, 15% кошика «art»
```

**Другорядний — спільні слова в заголовках.** Він слабший, і це перевірено: згорнувши `comedy`
назад в `art`, детектор за словами стендап **не побачив** — заголовки надто різні («Батя 2»,
«Просмажка Раміни», «СТЕНДАП СУБОТА»). Тип же видно одразу. Тому слова лишились як допоміжний
сигнал для нетипізованих подій, а рішення приймає тип.

Поріг подвійний: ≥15% кошика **або** ≥60 подій. Друга умова потрібна, бо у великому кошику навіть
90 подій дають частку 14.9% і не проходять на сотих відсотка — а це вже категорія за обсягом.

Скрипт **не вирішує**. Він показує число й приклади; восьма чи девʼята категорія коштує міграції
та роботи дизайнера на двох платформах, тож рішення лишається за людиною.

### Що він знайшов цього разу

`ChildrensEvent` — 91 подія, 15% кошика `art`. Дитяча програма має власну аудиторію (батьки
шукають саме її) і в спільній скриньці з драмою губиться так само, як губився стендап. Виділено
в категорію `kids`. Після цього звіт каже «жоден чужий тип не займає ≥15% кошика — розділяти
нічого»: кожен кошик тепер визначає його власний тип.
